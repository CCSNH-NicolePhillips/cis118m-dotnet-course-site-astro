## 🧠 What Is Nesting?

**Nesting** means placing one `if` block inside another. The inner block only runs if the outer condition is true:

```csharp
if (isLoggedIn) {
    // Only check permissions if the user is logged in
    if (hasAdminRole) {
        Console.WriteLine("Welcome, Administrator!");
    } else {
        Console.WriteLine("Welcome, standard user.");
    }
} else {
    Console.WriteLine("Please log in first.");
}
```

The inner `if (hasAdminRole)` is only reachable when `isLoggedIn` is `true`. This creates a **decision tree** — a branching hierarchy of conditions.

---

## 🏗️ When to Nest

Nesting is appropriate when the second decision **only makes sense** if the first condition is true:

```csharp
// Good nesting: inner check depends on outer
if (order != null) {
    if (order.Total > 100) {
        Console.WriteLine("Free shipping applied!");
    }
}
```

If `order` is `null`, checking `order.Total` would crash your program. The nested structure ensures safety.

<div class="pro-tip">
  <h4>💡 The Nesting Rule</h4>
  <p>Nest when the <strong>inner condition cannot be evaluated</strong> unless the outer condition is true. If both conditions are independent, use <code>&&</code> instead.</p>
</div>

## ⚠️ The Nesting Trap

Nesting is powerful but dangerous. More than **2-3 levels deep** creates an unreadable mess called the **"Arrow Anti-Pattern"** or **"Nesting Hell"**:

```csharp
// ❌ BAD: Arrow anti-pattern — too deeply nested
if (user != null) {
    if (user.IsActive) {
        if (user.HasSubscription) {
            if (user.Subscription.IsValid) {
                if (user.Subscription.Tier == "Premium") {
                    Console.WriteLine("Premium content unlocked!");
                }
            }
        }
    }
}
```

<div class="architect-rule">

#### ⚠️ Architect's Rule: Maximum 2 Levels of Nesting

If your code has more than 2 levels of nesting, it's time to refactor. Deep nesting is a code smell — it indicates your logic needs restructuring.

</div>

## 🛡️ The Guard Clause Pattern

**Guard clauses** invert the condition and exit early, eliminating nesting entirely. Instead of asking "if everything is okay, proceed," you ask "if anything is wrong, stop":

```csharp
// ✅ GOOD: Guard clauses — flat and readable
if (user == null) {
    Console.WriteLine("No user found.");
    return;
}

if (!user.IsActive) {
    Console.WriteLine("Account is deactivated.");
    return;
}

if (!user.HasSubscription || !user.Subscription.IsValid) {
    Console.WriteLine("No valid subscription.");
    return;
}

if (user.Subscription.Tier != "Premium") {
    Console.WriteLine("Upgrade to Premium for this content.");
    return;
}

// If we get here, everything is valid!
Console.WriteLine("Premium content unlocked!");
```

Notice how the "happy path" (the successful outcome) is at the **bottom** of the method, and all the rejection cases are handled first. This is much easier to read and maintain.

## 🔬 Try It: Nesting vs. Guard Clauses

Compare both approaches side by side:

<TryItNowRunner 
  starterId="week-07-lesson-1" 
  height={520}
  code={`using System;

class Program
{
    static void Main()
    {
        // Test data
        string username = "architect";
        bool isActive = true;
        int clearanceLevel = 3;
        
        Console.WriteLine("=== NESTED APPROACH ===");
        // Nested version (harder to read)
        if (username != "") {
            if (isActive) {
                if (clearanceLevel >= 3) {
                    Console.WriteLine("✅ Full access granted!");
                } else {
                    Console.WriteLine("⚠️ Insufficient clearance.");
                }
            } else {
                Console.WriteLine("🚫 Account deactivated.");
            }
        } else {
            Console.WriteLine("🚫 No username provided.");
        }
        
        Console.WriteLine();
        Console.WriteLine("=== GUARD CLAUSE APPROACH ===");
        // Guard clause version (flat and clean)
        if (username == "") {
            Console.WriteLine("🚫 No username provided.");
        } else if (!isActive) {
            Console.WriteLine("🚫 Account deactivated.");
        } else if (clearanceLevel < 3) {
            Console.WriteLine("⚠️ Insufficient clearance.");
        } else {
            Console.WriteLine("✅ Full access granted!");
        }
    }
}`}
  instructions="Both blocks produce the same result, but the guard clause version is flat and easy to read. Try changing the variables to test different paths!" 
/>

## 📐 When to Use Which Pattern

  <table>
    <thead>
      <tr>

        <th>Use When</th>
        <th>Example</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td><strong>Nested if</strong></td>
        <td>Inner condition <em>depends</em> on outer being true</td>
        <td>Check if object exists before accessing its properties</td>
      </tr>
      <tr>
        <td><strong>Guard Clause</strong></td>
        <td>You can <em>reject invalid cases early</em> and keep the happy path clean</td>
        <td>Validate inputs at the top of a method, then proceed</td>
      </tr>

        <td><strong>Flat &&</strong></td>
        <td>Both conditions are <em>independent</em> and simple</td>
