<div class="mission-brief">
  <h2>Mission Brief: System Integration Under Production Constraints</h2>
  <p>
    Week 15 is the capstone. No new language feature is introduced here. The engineering task is to integrate the architecture you have built since Week 10 into one coherent console application that accepts input, protects state integrity, manages collections correctly, and produces predictable operator output.
  </p>
  <p>
    The final project must behave like a single system, not a stack of disconnected code fragments. Methods partition controller logic. Return values drive decisions. Custom classes model domain entities. <code>List&lt;T&gt;</code> manages many objects. Encapsulated properties and constructor rules prevent invalid state. This week is about assembling those parts into a dependable runtime design and submitting a technically defensible final delivery.
  </p>
</div>

<div class="architect-rule">
  <h3>Senior Architect Perspective</h3>
  <p>
    Capstone work is not judged by feature count alone. It is judged by whether the system has clear boundaries. If input validation, collection management, state protection, and reporting all collapse into <code>Main</code>, the project is still a prototype. A production-minded submission shows where control lives, where data lives, and where invalid operations are stopped.
  </p>
</div>

## Final Project Technical Requirements

<div class="requirement-grid">
  <div class="requirement-card">
    <h3>Custom Class Architecture</h3>
    <p>At least one domain class must own real responsibility. The project cannot be implemented as primitive variables and free-floating helper code alone.</p>
  </div>
  <div class="requirement-card">
    <h3>Encapsulated Properties</h3>
    <p>Object state must be protected through validated properties, controlled constructors, or equivalent encapsulation that prevents invalid assignment.</p>
  </div>
  <div class="requirement-card">
    <h3>List-based Data Management</h3>
    <p>The system must manage multiple objects through a <code>List&lt;T&gt;</code>, including at least one lifecycle operation such as add, search, remove, update, or report.</p>
  </div>
  <div class="requirement-card">
    <h3>Modular Method Logic</h3>
    <p>Core behaviors must be decomposed into named methods with clear purpose and controlled data flow. A single oversized <code>Main</code> method is not sufficient.</p>
  </div>
</div>
