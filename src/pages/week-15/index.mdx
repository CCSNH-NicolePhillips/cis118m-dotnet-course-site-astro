  <p>

  </p>

## Integration Stack: Weeks 10-14 in One Runtime Design

<div class="styled-table-container">
  <table>
    <thead>
      <tr>
        <th scope="col">Prior Week</th>
        <th scope="col">Core Tool</th>
        <th scope="col">Final Responsibility</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td>Week 10</td>
        <td>Methods</td>
        <td>Partition controller behavior into named operations instead of collapsing all logic into <code>Main</code>.</td>
      </tr>
      <tr>
        <td>Week 11</td>
        <td>Return values</td>
        <td>Use method results to drive lookup, validation, and update decisions.</td>
      </tr>
      <tr>
        <td>Week 12</td>
        <td>Custom classes</td>
        <td>Represent the domain with objects rather than loose primitive variables.</td>
      </tr>
      <tr>
        <td>Week 13</td>
        <td><code>List&lt;T&gt;</code></td>
        <td>Manage multiple records through add, search, report, and update workflows.</td>
      </tr>
      <tr>
        <td>Week 14</td>
        <td>Encapsulation and constructors</td>
        <td>Reject invalid state before it enters or corrupts the running system.</td>
      </tr>
    </tbody>
  </table>
</div>

<div class="architect-rule">
  <h3>Senior Architect Perspective</h3>
  <p>
    Capstone work is not judged by feature count alone. It is judged by whether the system has clear boundaries. If validation, collection management, and reporting all collapse into <code>Main</code>, the project is still a prototype. Strong final work makes the control path obvious.
  </p>
</div>
