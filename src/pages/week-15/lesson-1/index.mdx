# 15.1 Global System Architecture

## Integration Objective

Week 15 begins with architecture, not code volume. Before you attempt final polishing, you need a system map that explains how control enters the program, how objects are created, where collections live, and which methods own each behavior. The objective is to turn the Weeks 10-14 toolset into one predictable runtime.

## Reference System Skeleton

```csharp
using System;
using System.Collections.Generic;

class InventoryItem
{
    private int _quantity;

    public string Name { get; }

    public int Quantity
    {
        get => _quantity;
        set
        {
            if (value < 0)
            {
                throw new ArgumentOutOfRangeException(nameof(value), "Quantity cannot be negative.");
            }

            _quantity = value;
        }
    }

    public InventoryItem(string name, int quantity)
    {
        if (string.IsNullOrWhiteSpace(name))
        {
            throw new ArgumentException("Name is required.", nameof(name));
        }

        Name = name.Trim();
        Quantity = quantity;
    }
}

static void RunMenu(List<InventoryItem> items)
{
    bool isRunning = true;

    while (isRunning)
    {
        Console.WriteLine("1. Add  2. List  3. Search  4. Quit");
        string command = Console.ReadLine() ?? string.Empty;

        switch (command)
        {
            case "1":
                AddItem(items);
                break;
            case "2":
                PrintReport(items);
                break;
            case "3":
                SearchItem(items);
                break;
            case "4":
                isRunning = false;
                break;
        }
    }
}
```

The important capstone lesson is not the sample domain. It is the separation of responsibilities. Control stays in the menu loop. State integrity stays in the class. Collection operations stay in methods that receive the list they need.

---

## Integration Sequence

1. Define the domain class first, including the properties and validation rules that make invalid state impossible.
2. Declare the <code>List&lt;T&gt;</code> that owns all runtime records for the application session.
3. Write one method per operator action: add, search, list, update, remove, save, or load.
4. Use return values for lookup and calculation operations so decisions are based on method results instead of duplicated logic.
5. Build the controller loop last, after the underlying methods and class contracts already exist.

---

## Boundary Failures to Eliminate

- Duplicating validation logic in multiple menu branches instead of centralizing it in the class.
- Creating objects directly inside report loops with no constructor contract.
- Storing parallel primitive lists instead of one <code>List&lt;CustomClass&gt;</code>.
- Printing inside every helper method when the method should return data to its caller.
- Allowing a single method to read input, mutate the list, calculate totals, and format reports all at once.
