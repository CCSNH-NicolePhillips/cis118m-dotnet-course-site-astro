## Homework 11: The Return Value Design Analysis

<p>You have worked with return-type methods this week — declaring return types, using the <code>return</code> keyword, and capturing results in variables. This reflection requires you to demonstrate <strong>analytical understanding</strong> of why methods return values, how the caller uses those values, and when to choose a return type over <code>void</code>. Engineering judgment, not a vocabulary list.</p>

## Reflection Prompt

<div class="component-cards">
  <div class="component-card">
    <h3>Return Value Design Analysis</h3>
    <p>In 3-5 sentences per question, answer the following:</p>
    <ol>
      <li>
        <strong>The Return Contract:</strong> Explain what the return type in a method signature promises to the caller. What does the <code>return</code> keyword do (two things)? What happens if a method declared as <code>static int GetTotal()</code> does not contain a <code>return</code> statement?
      </li>
      <li>
        <strong>void vs Return Type:</strong> Compare a <code>void</code> method and a method with a return type (e.g., <code>int</code>). When should you use <code>void</code>? When should you use a typed return? Give an example of a task that requires a return value and explain why <code>void</code> would not work for that task.
      </li>
      <li>
        <strong>Result Capture and Separation of Concerns:</strong> Explain the result capture pattern (<code>type variable = MethodCall(args);</code>). Why is it better for a calculation method to <em>return</em> a value rather than <em>print</em> it directly? How does separating computation from display make code more reusable?
      </li>
    </ol>
