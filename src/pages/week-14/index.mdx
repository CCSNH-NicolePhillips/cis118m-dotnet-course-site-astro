<DueDateBanner week={14} />

<div class="mission-brief">
  <h2>Mission Brief: From Exposed State to Engineered Integrity</h2>
  <p>
    Weeks 12 and 13 established the object model: custom classes, object instantiation, and collections. But those classes used auto-implemented properties with unrestricted public access — any code could set any value to anything, including a negative GPA, a blank product name, or a stock count of -500. Production systems cannot tolerate this. An object that can silently hold invalid state is a liability at scale.
  </p>
  <p>
    This week introduces two architectural mechanisms that control how objects are created and how their state changes after creation. <strong>Encapsulation</strong> — private fields with validated property accessors — makes it structurally impossible for external code to corrupt an object's data. <strong>Constructor overloading</strong> — multiple constructor signatures with the <code>this()</code> chaining keyword — enforces valid initial state from the moment an object is created. Together, these tools complete the object model: your classes become self-defending systems that enforce their own invariants.
  </p>
</div>

## The Object Architecture Shift

In Week 12, a `Student` class looked like this:

```csharp
class Student {
    public string Name { get; set; }
    public int Id { get; set; }
    public double Gpa { get; set; }
}
```

Nothing prevents `student.Gpa = -5.0`, `student.Id = -9999`, or `student.Name = ""`. These are syntactically legal. The class does nothing to stop them. The only way to catch invalid data under this design is to write validation in every place that creates or modifies a `Student` — and that guarantee will erode the moment the codebase has more than one author or one calling location.

Week 14 introduces the architectural response: move validation responsibility into the class itself. Private fields combined with validated set accessors create a hard boundary that external code cannot bypass. Constructors with required parameters make it impossible to instantiate an object without providing valid initial state. These two mechanisms together define a class that enforces its own contracts — a self-defending object.

<div class="architect-rule">

### Senior Architect Perspective

An object's state integrity is the class's responsibility, not the caller's. Validation scattered across <code>Main</code> and caller code is a maintenance defect: it duplicates business logic, guarantees drift between call sites, and fails silently when a new caller is added without the validation pattern. Centralize all integrity rules in the class: in <code>set</code> accessors for post-creation mutation, and in constructors for initialization. An object that can exist in an invalid state is not a finished class — it is a data structure waiting to be misused.

</div>
