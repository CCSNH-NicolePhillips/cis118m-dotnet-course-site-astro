## <span aria-hidden="true">🧠</span> Why Public Fields and Auto-Properties Fail

The simplest way to hold data in a class is a public field:

```csharp
class Product {
    public string Name;
    public double Price;
    public int Stock;
}
```

This compiles and runs, but provides zero protection. Any code anywhere can do this:

```csharp
Product p = new Product();
p.Price = -99.99;   // Negative price — legal C#, illegal business rule
p.Stock = -500;     // Negative inventory — no guard anywhere
p.Name = "";        // Empty name — passes through silently
```

The class holds invalid state and has no way to detect it. It will report a price of -99.99 to every system that reads it — checkout, invoicing, inventory reports — all of them downstream of a corruption that entered through a simple assignment.

Auto-implemented properties (`public double Price { get; set; }`) improve the syntax but not the safety. They are still unrestricted. The `set` accessor is implicit and performs no validation. Any caller can still assign any value. The only way to prevent invalid data under this design is to write validation in every calling location — and that guarantee erodes the moment the codebase grows, gains a second developer, or adds a new calling path that forgets the rules.

The architectural fix is to move the validation responsibility into the class. External code should encounter a hard boundary — not a convention that polite callers are expected to follow, but a structural barrier they cannot bypass.

---

## <span aria-hidden="true">🏗️</span> Private Fields and Public Properties

The encapsulation pattern replaces the exposed field with two elements: a **private backing field** and a **public property**. The field stores the data; the property controls all access to it:

```csharp
class Product {
    private double _price;

    public double Price {
        get { return _price; }
        set {
            if (value < 0)
                throw new ArgumentException("Price cannot be negative.");
            _price = value;
        }
    }
}
```

Now `_price` is invisible to external code. The `private` access modifier means only code written inside the `Product` class body can read or write it directly. External code must go through the `Price` property, and the `set` accessor applies the validation rule before any data reaches `_price`. If the value is invalid, the exception fires and `_price` is never touched.

The naming convention carries architectural meaning: private backing fields use a leading underscore and camelCase (`_price`, `_stock`, `_name`). Public properties use PascalCase (`Price`, `Stock`, `Name`). This convention is universal in professional C# codebases and immediately signals the access level and role of each member to any reader.

## <span aria-hidden="true">📐</span> The get and set Accessors in Depth

The `get` and `set` keywords define the two halves of a property's public interface. Understanding each independently reveals the full power of the pattern.

**The get accessor** executes when the property is read. In its simplest form it returns the backing field. But it can also derive a value from existing state on every read — a pattern called a **computed property**. A computed property has no backing field of its own; it calculates its value fresh from other fields every time it is accessed:

```csharp
class Product {
    private double _price;
    private int _stock;

    public double Price {
        get { return _price; }
        set {
            if (value < 0) throw new ArgumentException("Price cannot be negative.");
            _price = value;
        }
    }

    public int Stock {
        get { return _stock; }
        set {
            if (value < 0) throw new ArgumentException("Stock cannot be negative.");
            _stock = value;
        }
    }

    public bool InStock {
        get { return _stock > 0; }        // Derived — no backing field needed
    }

    public double TotalValue {
        get { return _price * _stock; }   // Derived — combines two fields
    }
}
```

`InStock` and `TotalValue` never go stale. Because they recompute on every read, there is no separate `bool _inStock` field that could drift out of sync when `_stock` changes. Computed properties eliminate an entire class of consistency bugs.

**The set accessor** executes when the property is assigned. The incoming value arrives in the implicitly-declared `value` variable — the same type as the property. This is where all validation logic belongs. The set accessor can also **normalize** the input before storing it:

```csharp
private string _name;

public string Name {
    get { return _name; }
    set {
        if (string.IsNullOrWhiteSpace(value))
            throw new ArgumentException("Name cannot be empty or whitespace.");
        _name = value.Trim();   // Normalize: strip surrounding whitespace before storing
    }
}
```

Normalization inside the set accessor means the backing field always holds clean data. Callers do not need to remember to `.Trim()` before assigning — the class enforces it. This is a demonstration of the Single Responsibility Principle: the class owns its own data consistency rules.

## <span aria-hidden="true">🏗️</span> From the Field: Product Catalog Validation

In a product catalog system, every `Product` entering the database must satisfy business rules: a non-negative price, a non-negative stock count, and a non-empty display name. These rules belong inside the `Product` class — not distributed across the checkout module, the inventory service, and the admin panel that all create and modify products. Moving validation out of the class means every caller must independently duplicate the logic, and duplication guarantees eventual divergence.

```csharp
class Product {
    private string _name;
    private double _price;
    private int _stock;

    public string Name {
        get { return _name; }
        set {
            if (string.IsNullOrWhiteSpace(value))
                throw new ArgumentException("Product name cannot be empty.");
            _name = value.Trim();
        }
    }

    public double Price {
        get { return _price; }
        set {
            if (value < 0)
                throw new ArgumentException("Price cannot be negative.");
            _price = value;
        }
    }

    public int Stock {
        get { return _stock; }
        set {
            if (value < 0)
                throw new ArgumentException("Stock cannot be negative.");
            _stock = value;
        }
    }

    public bool InStock {
        get { return _stock > 0; }
    }

    public double TotalValue {
        get { return _price * _stock; }
    }
}
```

Every assignment path goes through a guarded gate. `Name` refuses empty and whitespace-only strings and normalizes the stored value. `Price` refuses any value below zero. `Stock` refuses negative quantities. `InStock` and `TotalValue` are computed properties — no additional backing fields, no risk of stale derived state. The class is self-defending: there is no assignment path that can produce a `Product` with a negative price, regardless of which module performs the assignment.

<div class="architect-rule">

#### <span aria-hidden="true">⚠️</span> Architect's Rule: Validation Belongs in the Class, Not the Caller

Never place business rule validation exclusively in <code>Main</code> or in the calling code. If the validation lives outside the class, every call site must duplicate it. Callers will forget. Callers will disagree. New callers will be added without the pattern. Put validation in the <code>set</code> accessor once. From that point forward, no assignment anywhere in the codebase can store an invalid value. The class becomes a single source of truth for its own integrity rules.

</div>

#### <span aria-hidden="true">🎯</span> Predict the Output: Property Accessor Behavior

What does this code print? Trace each get and set call before running.

```csharp
class Temperature {
    private double _celsius;

    public double Celsius {
        get { return _celsius; }
        set {
            if (value < -273.15)
                throw new ArgumentException("Below absolute zero.");
            _celsius = value;
        }
    }

    public double Fahrenheit {
        get { return (_celsius * 9.0 / 5.0) + 32; }
    }
}

Temperature t = new Temperature();
t.Celsius = 100;
Console.WriteLine(t.Celsius);
Console.WriteLine(t.Fahrenheit);
t.Celsius = 0;
Console.WriteLine(t.Fahrenheit);
```

**Output**:
```

```

- `t.Celsius = 100` → set accessor runs, 100 >= -273.15 passes, `_celsius = 100`

<div class="pro-tip">
  <h4><span aria-hidden="true">💡</span> Pro Tip: Read-Only Properties with private set</h4>
  <p>Sometimes you want external code to read a property but never write it directly from outside the class. Declare the setter as <code>private set</code> — callers can read the value freely, but any assignment from outside the class is a compile-time error. Only methods inside the class can mutate the value. This is exactly the pattern in <code>BankAccountSafe</code>: <code>Balance</code> is readable by anyone but writable only by <code>Deposit</code> and <code>Withdraw</code>. The class controls all mutation paths.</p>
