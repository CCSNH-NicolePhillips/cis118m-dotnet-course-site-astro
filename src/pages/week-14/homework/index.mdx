# Homework 14: Technical Reflection — Object Architecture

<DueDateBanner week={14} type="Homework" />

## Reflection Prompt

In 3–5 sentences per question, answer all prompts with specific technical reasoning:

1. **The Firewall Concept:** Explain why placing validation logic inside the `set` accessor — rather than in `Main` or calling code — produces more maintainable and reliable software. Use the term "single source of truth" in your answer.

2. **Access Modifiers and State Integrity:** A `Product` class has `private double _price` and `public double Price { get; set; }` vs. `public double Price { get { return _price; } set { if (value < 0) throw ...; _price = value; } }`. What does the first version allow that the second version prevents? What category of bug does encapsulation eliminate?

3. **Constructor Overloading:** A registration system needs to create `Student` objects in three scenarios: full enrollment (name, ID, GPA), pre-registration (name and ID only), and roster import (name only). Explain how constructor overloading with `this()` chaining satisfies all three scenarios without duplicating validation logic. What is the maintenance risk if you duplicate the validation instead of chaining?

4. **Computed Properties:** Section 14.1 showed `bool InStock { get { return _stock > 0; } }` as a computed property with no backing field. Explain why a computed property is architecturally preferable to a stored `bool _inStock` field that is manually updated. Describe a specific scenario where the stored field would silently produce incorrect data.

Your answers should reason from architectural principles, not just syntax description. Explain the *why* and the *consequence* — what breaks without these patterns, and what becomes impossible to break with them.
