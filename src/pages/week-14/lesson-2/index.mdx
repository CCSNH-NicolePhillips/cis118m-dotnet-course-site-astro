## <span aria-hidden="true">🧠</span> What a Constructor Is and Why It Matters

A **constructor** is a special method that the C# runtime calls automatically every time an object is created with `new`. It shares the class's exact name, has no return type (not even `void`), and runs before any other code can interact with the new object. This makes it the correct place to establish initial state — not `Main`, not a separate `Initialize()` method, not a convention that callers are supposed to follow.

Without an explicit constructor, C# generates a hidden **default constructor** with no parameters that initializes all fields to their type defaults: `0` for numeric types, `null` for reference types, `false` for `bool`. This default constructor is what allows `new Product()` to work on a class that defines no constructor. The object is created in a zero-state that may or may not be valid for your domain.

Once you define your own constructor, C# removes the implicit default constructor. The compiler will reject `new Product()` with no arguments — which is precisely the enforcement you want. Callers must provide the required initialization data. There is no path to an underinitialized object.

```csharp
class Product {
    private string _name;
    private double _price;
    private int _stock;

    public Product(string name, double price, int stock) {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("Name cannot be empty.");
        if (price < 0)
            throw new ArgumentException("Price cannot be negative.");
        if (stock < 0)
            throw new ArgumentException("Stock cannot be negative.");

        _name  = name.Trim();
        _price = price;
        _stock = stock;
    }

    public string Name  { get { return _name; } }
    public double Price { get { return _price; } }
    public int    Stock { get { return _stock; } }
}
```

Now `new Product()` is a compile error. Every `Product` must be created with a name, a price, and a stock count — and all three are validated before the object is considered ready to use.

## <span aria-hidden="true">🏗️</span> Constructor Overloading

**Constructor overloading** means defining multiple constructors on the same class, each with a different parameter signature. The C# compiler resolves which constructor to call based on the argument types and count at the `new` expression. Overloading provides flexible creation paths without sacrificing the requirement to call a constructor — every path still goes through an initialization method, and every path can enforce its own rules.

A common use case: a product catalog where some products are always in stock and require all three values, while draft products might be created with just a name and price, defaulting stock to zero:

```csharp
class Product {
    private string _name;
    private double _price;
    private int _stock;

    // Full constructor — all three values required
    public Product(string name, double price, int stock) {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("Name cannot be empty.");
        if (price < 0)
            throw new ArgumentException("Price cannot be negative.");
        if (stock < 0)
            throw new ArgumentException("Stock cannot be negative.");
        _name  = name.Trim();
        _price = price;
        _stock = stock;
    }

    // Two-param constructor — stock defaults to 0
    public Product(string name, double price) {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("Name cannot be empty.");
        if (price < 0)
            throw new ArgumentException("Price cannot be negative.");
        _name  = name.Trim();
        _price = price;
        _stock = 0;
    }

    // Name-only constructor — price and stock both default to 0
    public Product(string name) {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("Name cannot be empty.");
        _name  = name.Trim();
        _price = 0;
        _stock = 0;
    }

    public string Name  { get { return _name; } }
    public double Price { get { return _price; } }
    public int    Stock { get { return _stock; } }
    public bool   InStock { get { return _stock > 0; } }
}
```

This design gives callers three valid creation paths while ensuring that a `Product` is never created without at least a name. But notice the problem: the validation logic for `name` is written in all three constructors. And the validation for `price` is in two of them. If the rule changes — perhaps names must be at least 3 characters — you must find and update all three locations. This is the classic duplicated-logic maintenance hazard that constructor chaining solves.

## <span aria-hidden="true">🔀</span> The this() Keyword: Constructor Chaining

The validation duplication in the overloaded constructors above is a real maintenance problem. The solution is **constructor chaining** with the `this()` keyword. A constructor can delegate to another constructor on the same class using `: this(arguments)` in its signature. The delegated constructor runs first, then control returns to the calling constructor's body (which can then add additional logic if needed).

The pattern is: write all validation in the most complete constructor, and have every simpler overload delegate to it with default values for the missing arguments:

```csharp
class Product {
    private string _name;
    private double _price;
    private int _stock;

    // MASTER constructor — owns all validation
    public Product(string name, double price, int stock) {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("Name cannot be empty.");
        if (price < 0)
            throw new ArgumentException("Price cannot be negative.");
        if (stock < 0)
            throw new ArgumentException("Stock cannot be negative.");
        _name  = name.Trim();
        _price = price;
        _stock = stock;
    }

    // Delegates to master — provides 0 as default for stock
    public Product(string name, double price) : this(name, price, 0) { }

    // Delegates to master — provides 0.0 and 0 as defaults
    public Product(string name) : this(name, 0.0, 0) { }

    public string Name    { get { return _name; } }
    public double Price   { get { return _price; } }
    public int    Stock   { get { return _stock; } }
    public bool   InStock { get { return _stock > 0; } }
    public double TotalValue { get { return _price * _stock; } }
}
```

Now validation exists in exactly one place — the master constructor. If a business rule changes, one edit propagates to all creation paths automatically. The two-param and one-param constructors have empty bodies (`{ }`) because their only job is to delegate to the master with appropriate defaults.

The `: this(name, price, 0)` syntax reads as "before running this constructor's body, call the constructor on this class that matches the signature `(string, double, int)` with these arguments." The master constructor runs first, validates everything, and assigns the fields. Then control returns to the delegating constructor's body — which is empty, so nothing else happens.

## <span aria-hidden="true">🏗️</span> From the Field: Student Registration System

In a student registration system, students can be created in multiple contexts: a full enrollment form with all details, a pre-registration with just a name and ID, or a roster import with name only and ID auto-assigned. Constructor overloading with chaining handles all three without duplicating the validation rules:

```csharp
class Student {
    private string _name;
    private int    _id;
    private double _gpa;

    // Master constructor — validates and initializes all state
    public Student(string name, int id, double gpa) {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("Student name cannot be empty.");
        if (id < 1000 || id > 9999)
            throw new ArgumentException("Student ID must be between 1000 and 9999.");
        if (gpa < 0.0 || gpa > 4.0)
            throw new ArgumentException("GPA must be between 0.0 and 4.0.");
        _name = name.Trim();
        _id   = id;
        _gpa  = gpa;
    }

    // Pre-registration — name and ID known, GPA starts at 0.0
    public Student(string name, int id) : this(name, id, 0.0) { }

    // Roster import — name only, ID and GPA set to defaults
    public Student(string name) : this(name, 1000, 0.0) { }

    public string Name   { get { return _name; } }
    public int    Id     { get { return _id; } }
    public double Gpa    { get { return _gpa; } }

    public string Status {
        get {
            if (_gpa >= 3.5) return "Honors";
            if (_gpa >= 2.0) return "Good Standing";
            return "Academic Probation";
        }
    }
}
```

`Status` is a computed property with no backing field: it derives a classification string from `_gpa` at read time. Changing a student's GPA through a validated setter would automatically change their `Status` on the next read — no manual update required. The entire chain — from the one-param constructor through the master constructor — runs the same validation rules, enforced once.

<div class="architect-rule">

#### <span aria-hidden="true">⚠️</span> Architect's Rule: One Constructor Owns the Validation

In a constructor chain, only the master constructor — the most complete overload — should contain validation logic and field assignments. Delegating constructors exist only to supply defaults and forward to the master. Placing duplicate validation in multiple constructors guarantees drift: when a rule changes, partial updates silently leave some creation paths broken. Write validation once, in the most complete constructor. Every other overload delegates to it.

</div>

<div class="pro-tip">
  <h4><span aria-hidden="true">💡</span> Pro Tip: this() vs. Repeated Initialization</h4>
  <p>When you have multiple constructor overloads, always favor <code>: this(...)</code> chaining over duplicating initialization code across constructors. Duplication in constructors is especially dangerous because it is easy to update one and forget another — and the bug is silent: all constructors compile, all create objects, but different paths produce different behavior. If a validation rule or default value ever needs to change, chaining ensures exactly one edit updates all creation paths simultaneously.</p>
