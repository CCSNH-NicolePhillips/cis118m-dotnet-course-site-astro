<DueDateBanner week={10} type="Lab" showLatePolicy={false} />

<div class="mission-brief">
  <h2>🔧 Welcome to Modular Programming</h2>
  <p>
    Every program you have written so far lives inside a single <code>Main</code> method. That works for small programs — but it does not scale. This week you begin <strong>modular programming</strong>: the practice of breaking a program into named, reusable methods, each responsible for exactly one job.
  </p>
  <p>
    Think of a method as a department in a company. The company (your program) has a name. Each department (method) has a job title (<strong>identifier</strong>), a list of resources it needs to do its job (<strong>parameters</strong>), and a defined output it delivers (<strong>return type</strong>). You do not re-hire and re-train the same team every time a task is needed — you <em>call the department</em>. This is the <strong>DRY Principle</strong>: Don't Repeat Yourself.
  </p>
</div>

## 🏗️ The Architecture Upgrade: One Method → Many

Until now, your programs have executed as a single block of code from top to bottom inside `Main`. This week you learn to extract logic into separate methods — each with a precise contract that defines what it needs and what it provides.

<img src="/media/week%2010/10.0/The%20Modular%20Shift.jpeg" alt="The Modular Shift — monolithic Main method on the left transforming into organized modular methods on the right" style="max-width: 100%; border-radius: 12px; margin: 24px 0;" />

<div class="component-cards">
  <div class="component-card">
    <h3>🧱 Monolithic (Before)</h3>
    <p>All logic inside <code>Main</code>. As programs grow, this becomes unreadable, untestable, and impossible to reuse. The same logic appears in multiple places — any change must be made everywhere.</p>
    <code>static void Main() &#123; // Everything crammed here &#125;</code>
  </div>
  <div class="component-card">
    <h3>🏗️ Modular (After)</h3>
    <p>Each responsibility lives in its own method with a clear name. <code>Main</code> becomes an orchestrator — it calls departments rather than doing all work itself. Change a department once; it updates everywhere it is called.</p>
    <code>static void PrintHeader() &#123; ... &#125;</code>
  </div>
</div>

## 🏗️ Senior Architect Perspective

<div class="architect-rule">

### ⚙️ The DRY Principle Is a Maintenance Contract

When you write the same logic in two places, you create a maintenance liability: every time that logic needs to change, you must find and update every copy. If you miss one, the program behaves inconsistently. The DRY Principle — **Don't Repeat Yourself** — is not about saving keystrokes. It is about creating a single source of truth. When logic lives in exactly one method, a correction made there applies everywhere the method is called.

🎯 **The most common failure this week will be copy-paste programming** — duplicating code blocks instead of extracting them into a named method. If you find yourself writing the same lines twice, that is the signal: make it a method.

</div>
